Lane 1 — Briefing-40 Tier-2.1 lands: Group S phase-split halves cold-boot op-reads

MEMO-2026-06-08-mi7m — Fast-phase integrity-check skips Group S op-reads (S3/S4/S7); live phase keeps full coverage. Landed via #1340 (memo) + paired with coo-harness#583 (implementation, closes coo-harness#563). Issued 2026-06-08 12:55. The scripts/boot/integrity-check.sh Group S now splits along the phase boundary, matching the existing Group E pattern: the op-touching invariants — S3 (mirror sha8-compare), S4 (multi-field op item get), S7 (primary+alt-field op read walk) — fire only when VADE_INTEGRITY_PHASE != "fast". Cheap structural checks (S1/S2/S5/S8/S9/S10) stay in both phases.

Root cause from briefing-40 instrumentation. The T2.1 day-of-record data showed three cold-boot sessions burning 60-85 op-reads each — 3-4× the briefing’s documented bound. The per-source breakdown traced the bulk of the unaccounted volume to integrity-check.sh Group S firing twice per cold boot (~25-30 op-reads each pass) because the script runs from coo-bootstrap.sh’s EXIT trap (fast phase, blocking boot banner) and again from post-bootstrap-chain.sh (live phase, backgrounded), and only Group E was gated by the phase flag. The split halves the integrity-check contribution on cold boot and brings the expected total to ~32 reads on a 2026-06-07-shaped workload, clearing Phase-3’s <40 target.

Boot-banner side effect. integrity-check.json now shows S3/S4/S7: skip phase=fast: op-bound check deferred to live pass for the ~5-10s window between banner render and live-phase completion. Consumers reading after the live phase lands (boot brake, /verify-secrets, debug-mode skill) see the merged result. New scripts/ci/test-integrity-phase-gate.sh asserts the dispatch behavior under each phase value (19 assertions, all pass) and lands in .github/workflows/bootstrap-regression.yml between the existing bootstrap-op-caches and bootstrap-allowlist-sync tests.

Verification posture. Phase-3 close-out (rerun the rollup on the next post-merge cold-boot, target <40 reads) requires a fresh container snapshot built off this PR. The rerun lands as a follow-up comment on coo-harness#583 once a post-merge cold-boot session has generated a new .op-reads.jsonl.

Net effect of Lane 1: briefing-40’s Phase-1 root-cause investigation (instrumentation: coo-harness#542 + #563) made the two-phase double-billing diagnosable; the Phase-2 consolidation (mi7m + coo-harness#583) eliminates the double-bill deliberately rather than coincidentally. The Group E pattern was the precedent — Group E op-touching invariants were already phase-gated; the gap was that Group S was missed when the phase-split convention was first introduced. mi7m closes that gap and brings cold-boot op-read consumption from 3-4× the documented bound to within target. Phase-3 verification gates on the next post-merge cold-boot signal; until that lands the reduction is calculated from the per-source breakdown, not observed.

Lane 2 — Harness-portability plan Track 1: single environment discriminator established as case-law

MEMO-2026-06-08-kx7r — VADE_HARNESS_PROVIDER as single environment discriminator. Landed via #1330 (memo only — no code change in this PR). Issued 2026-06-08 06:36. Establishes VADE_HARNESS_PROVIDER ∈ {anthropic-cloud-web, local-mac, linux-vm} as the canonical single discriminator for the environment the harness is running in. Each provider exports the signal at session start before any harness script runs: cloud-web via the Anthropic container UI’s .env-block, local-mac via the dotfiles claude-coo() wrapper, linux-vm via TBD (deferred until needed).

Replaces three ad-hoc mechanisms. Today’s harness discriminates between cloud-web and other environments via three scattered checks: CLAUDE_CODE_REMOTE=true env probe (coo-bootstrap.sh:95), _is_cloud_context() filesystem fingerprint (lib/common.sh:50), and per-script uid==0 && -d /home/user checks (lib/common.sh:741, lib/common.sh:781). These work today only because cloud-web is the only is-cloud path actually exercised; adding a third environment forces a refactor of scattered checks across the script tree. The memo formalizes the single-discriminator design before the third environment gets introduced.

Provider contract scope. Lifecycle shape, workspace root, identity-injection source, bindir, tmpfs availability, and integrity-check group skip behavior land alongside in operations/provider-matrix.md (to be drafted as a follow-on; the memo names the contract surface, the file populates it).

Migration is staged. _is_cloud_context() survives as a helper but its implementation switches to read $VADE_HARNESS_PROVIDER. Each consumer migrates as part of its track. Track 1 (this memo) is decision-level case-law; Tracks 2-4 implement the migration to the new signal; Track 6 (substrate-side hygiene) is filed as coo-harness#573, #574, #575, #576. Relates: coo-harness#274 (env-block delivery channel) and coo-harness#573 (VADE_RUNTIME_DIR injection reliability — sibling concern using the same env-block pathway).

Net effect of Lane 2: the harness-portability plan that ran its audit pass on 2026-06-07 ships its first concrete case-law deliverable — a single environment-discrimination signal, sourced uniformly across providers, replacing three ad-hoc mechanisms that work today only by accident of cloud-web being the only exercised non-default path. The memo is decision-only, not implementation — no code touched in #1330 — which is the correct shape for the layer: the discriminator’s name and contract needs to be settled before the migration PRs that read it can land. The provider-matrix file becomes the next concrete artifact under this lane; the per-consumer migration PRs (Tracks 2-4) follow as the substrate consumers each pick up the signal in their own scope. The arc shape — audit → name the discriminator → populate the contract file → migrate consumers — mirrors the briefing-040 arc (claim → audit → followup plan → memo’d reductions → delivered), at a longer wall-clock cadence because the migration touches more surface area.
